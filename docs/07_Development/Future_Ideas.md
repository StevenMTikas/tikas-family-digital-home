# Future Ideas

## Purpose

A running collection of ideas, features, and enhancements that are explicitly **out of scope for MVP** but worth remembering. Some are pulled from "Future Enhancements" sections scattered across other documents (consolidated here for one place to browse); others are new feature concepts that fit the project's philosophy but haven't been scoped into a module yet. This is a living document — expected to grow throughout development.

## ⭐ Next Up — Do These First

Flagged by Steven (2026-08-03) as the first things to complete, for two different reasons:

- **Items 1–2 are unanswered questions, not features** — they get harder to fix the longer real family data accumulates, and the failure in both cases is silent.
- **Items 3–5 are small, self-contained builds with outsized day-to-day payoff** — each one is a field, a link, or an error message away from real value that's currently sitting unused or actively confusing someone.

- **⭐ 1. Succession / continuity — "what happens if the Super Admin isn't here."** The single biggest gap in the current design, and a real single point of failure in the architecture as actually built, not a hypothetical. There is exactly one Super Admin (Dad); backups are encrypted with a `BACKUP_ENCRYPTION_KEY` that lives only in `.env.local` (`lib/core/backup`, `lib/crypto/secret-box.ts`); Password Entries are encrypted behind a key derived the same way; and there is deliberately no password recovery (`Authentication.md`). If the Super Admin were suddenly gone, the rest of the family would be left with a house full of encrypted records they cannot open and no path to promoting a new Super Admin. For a project whose stated purpose is to **protect a family's knowledge** long-term (`Vision.md`), having no answer to "the keyholder is gone" is a genuine hole. Likely shape: a designated successor admin plus a documented, actually-tested break-glass procedure for key recovery — the testing matters as much as the mechanism, since an untested recovery path is indistinguishable from no path. Needs its own design pass; interacts directly with `Security_Architecture.md`, `Authentication.md`, `Authorization.md`, and `Backup.md`.
- **⭐ 2. The minor → adult transition.** `date_of_birth` is stored (`db/schema.sql:21`) and the minor gates are enforced in application logic (`db/schema.sql:41` — "Never 1 for a minor — enforce in application logic, not just this default"), including `AI_Permissions.md`'s hard rule that the sensitive-data outside-transmission gate can *never* be granted to a minor. But nothing anywhere defines what happens on a child's 18th birthday. Either those gates quietly unlock with nobody deciding anything, or they stay locked forever and silently become wrong — both are bad, and the failure is invisible either way. A parent should get an explicit prompt to review and decide, not have it happen (or not happen) unnoticed. Small to build, but it needs a real decision about intended behavior first — and it becomes materially harder to reason about the longer the account has accumulated history under minor-scoped rules.
- **⭐ 3. "Go to site" deep link on Tasks/Events.** Motivated by a real want: for a Budget-category event/task (e.g., a bill due), a one-click way to jump straight to the biller's site rather than hunting down the URL. Real automated login (the app holding/entering a password itself) was explicitly considered and **rejected** — it would mean Tikas handling decrypted credentials in-process against a live third-party site, a real expansion of risk this project has avoided everywhere else (Family_Knowledge's Password Entries are AES-256-GCM encrypted specifically so the password itself never moves around loosely), and many billers' own terms of service prohibit automated login even by the account holder. **The deep link is the whole feature, deliberately not a login flow:** add an optional `url` field directly to Task and Event (`Data_Model.md`), and whenever it's set, show a "Go to site" link/button wherever that item already appears (list row, detail view, and the reminder notification itself). Clicking it just opens the real URL in a new browser tab — no credentials touch Tikas at all; the user's own browser autofills the saved password exactly as it would from a bookmark, and 2FA is handled by the person as normal. Small, self-contained, no new subsystem — just a field + a link.
- **⭐ 4. Graceful degradation when a dependency is down.** Surfaced by real usage, not theory: with Ollama not running, the Assistant returned only "The Assistant hit an error responding. Please try again," with no indication that the actual problem was a service that simply wasn't started. Nothing in the docs defines intended behavior when Ollama is unreachable, the host is down, or a phone connector is offline — so *every* failure looks identical to a bug from a family member's perspective, which quietly erodes trust in the whole app. Guardian already computes real system-health data (`computeHealthSnapshot()`, disk/device/backup checks), so the app is fully capable of saying *what* is actually wrong and whether it's something a family member can fix or should just wait out. Worth a consistent, app-wide treatment rather than per-module error strings.
- **⭐ 5. Bulk download of fetched documents.** Every download today is one file at a time via a plain `<a>` link (`app/api/documents/[id]/download/route.ts`, `app/content/ContentPageClient.tsx`) — no multi-select, no "download all"/zip export. Fine for a handful of files, painful for something like a whole semester of homeschool documents (Steven's flagged use case, 2026-07-29). **Moved up specifically because the homeschool/education module is the next real feature build** — adding a system that generates school documents in volume before fixing one-at-a-time download makes the pain worse, not better.

## New Feature Concepts (Not Yet Tied to a Specific Module Doc)

Ideas that build naturally on the existing architecture (Advisor suggestions, Family Knowledge, Memory, Assistant) without requiring new subsystems:

- **Household inventory nudges** — Advisor suggests restocking based on patterns in usage/mentions.
- **Escalating birthday/anniversary reminders** — beyond a calendar event, Advisor proactively suggests gift ideas or reservations ahead of time, based on AI_Memory patterns.
- **Maintenance reminders from Family Knowledge** — e.g., flagging an HVAC filter change or an insurance renewal, using the same weekly-check pattern Guardian already runs.
- **3D printing project follow-through** — Advisor flags a stalled project the same way it flags stalled Tasks (a personal touch specific to this family's interests).
- **"On this day" memories** — surface a Memory from a prior year on its anniversary, using existing Memory/Photo entities and a Guardian-style scheduled check.
- **Auto-suggested Memory ↔ Family Knowledge linking** — e.g., linking renovation photos to the related home-improvement record.
- **Emergency info quick-view** — an always-accessible view of just the most critical Family Knowledge items (medical contacts, allergies, emergency contacts), without digging through folders.
- **Chore/responsibility tracking** — recurring household responsibilities (distinct from one-off Tasks), with light AI nudging when something's been skipped.
- **"Ask the house" as a flagship Assistant use case** — highlighting queries like "what's everyone doing this weekend" once enough family data has accumulated to make this genuinely useful.
- **Voice-first mode** — for hands-busy moments (cooking, driving, chores), building on the planned Voice module and the "every screen supports voice where practical" rule.
- **Family meeting/check-in mode** — a structured weekly view, possibly tied to the family-wide Morning Briefing, meant to be reviewed together rather than individually.
- **Guardian-flagged "quiet" patterns as a gentle prompt, not just a report** — e.g., a low-key nudge to the person themselves ("haven't seen you in a bit") rather than only a fact surfaced to parents, keeping the tone about connection rather than surveillance.
- **Personal journal feature** (2026-07-30, Steven's idea) — a private-by-default place for a family member to write freeform entries (a day's events, thoughts, a kid's homeschool reflection), separate from Memory (which is more curated/photo-centric) and Family Knowledge (which is reference info, not a running log). Would need its own entity — probably `journal_entries` (user-scoped, date, text, optional mood/tag). Own visibility rules too (default private to the author, not the "public/private" family-wide model Events/Tasks use). **Sensitivity nuance flagged by Steven (2026-07-30):** existing `is_sensitive` (`AI_Permissions.md`) gates one specific thing — the extra approval required before sensitive data leaves the home to an outside frontier model. Journal content is a different kind of private: the concern is other family members / in-household AI use (Advisor surfacing it, Guardian's passive scanning, AI_Memory drawing inferences from it), not just outside transmission. Reusing `is_sensitive` as-is would conflate the two. Worth a real design pass on whether journal entries need a second, distinct flag/category (e.g. something like "excluded from Advisor/Guardian scanning" separate from "gated for outside transmission") rather than just marking them `is_sensitive` and calling it done. Needs its own scoping pass — not yet designed.
- **Notes feature** (2026-07-30, Steven's idea) — lighter-weight than the journal above: quick, ad-hoc freeform notes rather than dated personal reflections. Closer in spirit to a sticky-note/scratchpad — not necessarily private (could be personal or shared with the family, unlike the journal's private-by-default model), not necessarily tied to a specific date. Distinct from Family_Knowledge_Item, which is more structured reference info (a category, a title, meant to be looked up later) than a quick capture. Needs its own scoping pass — not yet designed, including how/whether it overlaps with Family Knowledge and Tasks enough to reuse existing patterns instead of a new entity.
- **Document expiration & renewal tracking** (2026-08-03) — passports, driver's licenses, insurance policies, vehicle registrations, professional certifications. Distinct from the "maintenance reminders from Family Knowledge" bullet above, which is framed around recurring upkeep (HVAC filters) rather than a hard expiry date on a specific stored document. Mostly wiring together pieces that already exist: an optional `expires_on` field on Document (`Data_Model.md`), Advisor's existing scheduled-check pattern (`advisor.ts`'s plain-SQL detection, same shape as `detectTasksNearingDue`), and the existing Notifications path. High practical payoff for a comparatively small build, and it makes `Vision.md`'s "protect their knowledge" promise concrete rather than abstract.
- **Time capsule / future-dated messages** (2026-08-03) — write a letter or record a memory intended for delivery on a specific future date (a child's 18th birthday, a graduation, an anniversary). Deliberately distinct from the "On this day" bullet above, which looks *backward* at content that already exists; this creates something aimed *forward* on purpose. Technically close to free — the reminder scheduler (`scripts/scheduler-reminders.ts`), Notifications, and the Memory module already provide everything needed; the real design questions are visibility (hidden from the recipient until its delivery date, which no existing entity does — even private items are visible to *someone* today) and what happens if the author is no longer around to send it (ties directly into the succession item at the top of this document).
- *(Graceful degradation and the "Go to site" deep link were moved up to **⭐ Next Up — Do These First** at the top of this document, 2026-08-03.)*

## Outside Frontier Model — Other Candidate Uses

Beyond the photo-to-event extraction feature already built into `Assistant.md` (see `Decision_Log.md` #007), other tasks that would genuinely benefit from a frontier model's greater capability, following the same outside-call approval pattern:

- Document extraction beyond flyers (insurance cards, medical forms, tax documents, receipts).
- Handwriting recognition (school notes, handwritten recipes, doctor's notes).
- Voice transcription in noisy/complex conditions (multiple speakers, background noise, accents).
- Large-scale photo search/tagging (e.g., face/scene recognition across thousands of photos) beyond the simple manual-prompt tagging built for MVP.
- Complex reasoning over long documents (e.g., summarizing a lengthy insurance policy or contract).
- Recipe/meal-plan generation from a photo of fridge/pantry contents.
- Translation for non-English documents or conversations, if relevant to the family.
- ~~**Hybrid local/frontier Assistant routing**~~ — **built 2026-08-01**, now documented as real behavior in `AI_Architecture.md` and `Assistant.md` (design refined across several conversations starting 2026-07-31). Motivated by a real, reproduced problem: `llama3.1:8b` sometimes leaks system-prompt fragments (the tool-use instruction, AI_Memory's "no stored facts about this person yet" placeholder) into user-facing replies and spirals into incoherent output — reproduced live asking the Assistant for the plain text of a Bible verse, a question that never needed tools or family data in the first place. Two complementary mechanisms shipped:
  1. **Automatic routing for a conversation stretch needing no family data, no approval prompt** (`lib/core/ai/frontier.ts`'s `streamFrontierReply`, wired into `streamAssistantReply` in `lib/core/ai/index.ts`) — reuses `messageNeedsTools()` to decide, before offering `ASSISTANT_TOOLS`/AI_Memory context to the model at all, whether the question plausibly needs either. If not, it routes straight to the frontier model — modeled on `Dashboard.md`'s Weather Standing Integration Connection (set up once, then flows automatically with no per-instance approval), since nothing family-specific is ever in the payload. **Revised 2026-08-01** (Steven reported "the assistant doesn't see previous chats" — traced to the original single-bare-question design, no history at all, breaking any follow-up like "and verse 4?"): the classification and payload now both cover a short recent window (`FRONTIER_HISTORY_WINDOW`, last 6 messages) instead of just the newest one — every message in the window has to pass the no-family-data check, and if it does, that window (real conversation turns, still never AI_Memory) is what gets sent, restoring continuity without weakening the guarantee an earlier turn drifting into family topics still forces a local fallback.
  2. **Thumbs-down escalation for questions that do use family data** (`lib/core/ai/frontier.ts`'s `escalateToFrontier`, `app/api/assistant/conversations/[id]/messages/[messageId]/escalate/route.ts`) — new per-message thumbs up/down UI on `AssistantBubble.tsx`, distinct from the pre-existing `AI_Suggestion`-card feedback (`AI_Suggestions.md`). On thumbs-down (only offered for a local-sourced reply, and only to a user holding both permissions below), a preview step shows exactly what would be sent — the original question, the specific AI_Memory facts, and the local model's own answer — before the user confirms and it's actually sent.
  - **Approval reuses the existing "Approve Outside Calls" permission** (`Authorization.md`) plus the sensitive-data outside-transmission gate (`AI_Permissions.md`) — AI_Memory content is treated as sensitive by default whenever it's sent outbound, the same way photo-to-event extraction already is, so it's categorically unavailable to a minor's account regardless of whether "Approve Outside Calls" is ever granted to them. A user holding neither permission never sees the escalate option at all (`canEscalate` on the conversation-detail API).
  - **Provider for now: Anthropic only** (`claude-opus-5`, via `@anthropic-ai/sdk`, `ANTHROPIC_API_KEY`) — Steven's explicit direction (2026-08-01): *"For right now I would like it to escalate to claude but in a commercial release a user should be able to choose which frontier model is chosen. They will have to provide an API key themselves for whichever frontier model is used."* **Deferred to a commercial release:** letting each household pick its own frontier provider (Anthropic/OpenAI/etc.) and supply its own API key, rather than the single hardcoded provider/key shipped for MVP. Would mean generalizing `frontier.ts` behind a provider interface instead of calling the Anthropic SDK directly, plus a settings screen for entering/rotating a household's own key(s) — not yet designed.

## Adjacent Products & Platform Extensions

Ideas for separate products or add-ons that build on this platform, surfaced 2026-07-27 while discussing the phone connector's architecture. Two overlapping items already have their own entries elsewhere in this doc and aren't repeated here: the **family assistant robot** (see Physical / Hardware Direction, above) and the **AI personality content channel** (see Commercial / Marketing Ideas, below).

**Reuse most of the existing architecture as-is:**

- **Smart-home hub integration** — bridging to Home Assistant (Matter/Zigbee/Z-Wave support already solved there) rather than writing device-specific connectors for doorbells/thermostats/appliances. The file-connector model doesn't fit smart-home devices directly: it's file-centric (not event/telemetry-centric), pull-based on a lazy schedule (wrong for "someone's at the door right now"), and one-directional (no way to send a command like "set to 70°" back to a device). Most consumer smart-home devices also don't expose a local API at all — they require going through the manufacturer's cloud, which conflicts with this project's local-first approach everywhere else (Ollama, Tailscale, SQLite). A real, separate subsystem, not a small extension.
- **Wall-mounted "family command center" display** — the Dashboard/Morning Briefing already exists and is designed for exactly this. Run it in kiosk mode on a cheap tablet or a Raspberry Pi + touchscreen in the kitchen. Cheapest item on this list to validate — mostly hardware packaging, almost no new software needed.
- **Turnkey home-server appliance** — package the whole stack (this app + Ollama + SQLite) as pre-configured hardware, like a Synology NAS or a Home Assistant Yellow/Green box. Directly closes the "non-technical installer" gap already flagged for connectors above. Real engineering (installer/provisioning work), but packaging what already exists rather than a new product concept.
- **Multi-household / self-hostable commercial version** — less a new idea than the eventual destination already implied throughout this document and `Decision_Log.md`'s repeated "if this becomes commercial" notes; listed here as its own line item since it's a distinct product decision, not just a checklist of hardening tasks.
- **Google Drive/Dropbox connector, client-direct only — for a future paid cloud tier's photo handling.** For a commercial cloud tier (where a family trades some local-only privacy for a hosted model at a monthly fee), extends the existing "metadata first, files on demand" connector pattern (`File_Connector_Architecture.md`) to cloud storage the family already has, instead of Tikas's own servers storing photos directly — especially relevant for children's photos. Two implementation paths were considered: **server-mediated (the Tikas host fetching the file from Drive/Dropbox on request, matching the existing computer/phone connector pattern) was rejected** — even a transient, on-demand fetch means Tikas's servers receive and handle the actual file bytes and associated metadata, which likely carries real custodial/compliance obligations similar to hosting the photo directly. **Client-direct is the intended approach instead**: the browser talks straight to Drive/Dropbox using the user's own OAuth token (Google Picker API / Dropbox Chooser), and Tikas only ever stores a file ID/link + metadata — the actual bytes never pass through Tikas's servers at all. Not yet scoped, and real legal review would still be needed before any commercial build — this is an architectural direction, not a legal conclusion (Steven, 2026-07-31).

- **Auto-generated family yearbook / "year in review"** — once real family photos are flowing through the connectors, generate an annual printed or digital keepsake (Chatbooks/Shutterfly-style) from Memory + Photos + Family Knowledge. A genuinely different business (photo-book printing/fulfillment) built on the same underlying data, not just a feature.

## Commercial / Marketing Ideas

- **AI "personality" channel for promotion** (Steven's son's idea, 2026-07-26) — if this becomes a commercial product, give the AI its own public-facing presence (a YouTube/social channel, similar to how some pets get their own accounts), narrating its own reasoning in first person to give the "AI brain" a personality as a promotional hook. **Feasibility note:** the app doesn't currently capture a distinct "internal thought process" to repurpose — the local Llama models aren't reasoning models with a visible chain-of-thought, and Guardian/Advisor's detection logic is plain deterministic SQL with the LLM only phrasing the final finding. So this would mean *generating* first-person narration from an already-logged interaction (a new prompt/voice layer, reusing the existing `base-layer.ts`/`roles.ts` pattern — low-to-moderate engineering effort, maybe a couple of days for a first draft pipeline), not surfacing something that already exists. The real work is (1) designing a consistent, watchable personality/voice — a writing/branding exercise, not code — and (2) mandatory privacy curation/anonymization before anything with real family data (names, health notes, schedules) goes into public content. Actual video production (TTS, animation, editing) is a separate toolchain entirely, outside this codebase.
- **Commercial billing model: pay-per-use with Tikas's API key, or bring-your-own key/storage** (Steven, 2026-08-01). For AI compute — building on the frontier-routing infrastructure above (`lib/core/ai/frontier.ts`) — the default is Tikas's own API key, billed pay-per-use to the household; a Super Admin can instead switch to a household-supplied API key, in which case that household maintains its own balance directly with the provider (Tikas bills nothing for compute in that mode) and gets to choose which frontier model/provider to use. When Tikas's own key is used, Tikas selects whichever model currently gives the best price/accuracy combination per its own running metrics, rather than the household picking — this requires a real evaluation pipeline: a sampled subset of responses routed to human moderators who judge which model's answer was best, feeding a running per-model quality score that drives the automatic selection. A parallel two-tier model applies to storage: store their own documents at no storage cost (e.g., via the client-direct Google Drive/Dropbox connector above), or pay Tikas a premium to store documents directly on Tikas's own servers. Needs real scoping before build: billing/metering infrastructure, a moderator review workflow and its own UI, a model-quality-metrics store, and a decision on what happens to already-stored data if a household switches tiers later.

### Permissions & Security
- **Real device-gated login** — identify the browser/device attempting to log in and block anything not explicitly Super-Admin-approved, independent of network-layer access. Discovered during Phase 7's testing pass that `Authentication.md` had described this as an MVP hard requirement, but it was never actually built and isn't part of `Security_Architecture.md`'s real Device Trust model (which is scoped to file-connector devices only, not family-member login) — corrected the doc to match what's actually built (username/password only). This is a real requirement to build before any commercial/multi-household release, not optional polish — a shared/public network can't lean on "only people with Tailscale access can reach this at all" the way this single household's MVP does (`Authentication.md`, `Security_Architecture.md`)

### Voice
- **Wake word must ship with no default, forcing an explicit choice during initial (Super Admin) setup** — not a generic fallback the family never actively picked. Builds on `Voice.md`'s existing "user-configurable wake word" Future Enhancement, adding the specific requirement that there be no default at all. Should live in Super Admin settings alongside the household/product display name, as a peer setting rather than a one-time setup-only choice — either should be changeable later, not locked in at first launch (Steven, 2026-07-30).
- **Higher-quality TTS via ElevenLabs or an equivalent voice model, replacing the browser's built-in `speechSynthesis`.** Current voice output (`AssistantBubble.tsx`'s `speak()`) uses the Web Speech API's `SpeechSynthesisUtterance` — free and already working, but robotic and inconsistent in quality across OS/browser. A commercial-grade voice model would sound dramatically more natural, at the cost of becoming a real outside call (reply text leaves the home, per-call or subscription cost, API key required) — the same tradeoff shape as the local-speech-to-text-vs-Google gap already flagged under Technology & Hosting above, just on the output side instead of input. Would need its own decision on whether it's opt-in per household (a Standing Integration Connection, same pattern as Weather) rather than a silent default, since reply text can carry real family context (Steven, 2026-08-01).
